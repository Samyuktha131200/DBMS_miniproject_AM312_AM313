# MongoDB data model

This document describes the NoSQL part of the Hospital Emergency Management System:
why MongoDB is used, what is stored in it, how it is validated, indexed, queried and
protected, and how it stays consistent with the MySQL database.

## 1. Why two databases

The relational schema (`01_schema.sql`) holds data with a **fixed structure and
strong relationships**: patients, departments, doctors, staff, ambulances, beds,
emergency cases, treatments, prescriptions, test orders and bills. These need
foreign keys, joins and transactions across many tables, so MySQL is the right tool.

Three kinds of emergency-room data do not fit that shape well:

| Data | Why it is awkward in MySQL | Why MongoDB fits |
|---|---|---|
| **Incident reports** (ambulance call-outs and in-hospital safety incidents) | Each incident type records different facts (a road crash has vehicles and extrication time; a medication error has the drug and the dose). One table would need dozens of mostly-NULL columns, or an entity-attribute-value design. A report has a variable-length timeline and can involve several patients. | One document per report. The common fields are validated strictly; `details` holds the type-specific facts. The timeline is an embedded array, and `case_ids` is an array with a multikey index. GeoJSON location supports `$geoNear` hotspot analysis. |
| **Observation logs** (vital signs) | High-volume, append-only readings, where each source (ambulance, triage, ward) records a different subset of vitals plus situation-specific extras (peak flow, pupils, burn area). | A sparse `vitals` object stores only what was measured. The NEWS2 score is calculated in an aggregation pipeline (`$switch`, `$setWindowFields`), so there is no stored score to go stale. |
| **Clinical notes** | Long free text, with an optional structured part (SOAP sections), tags, and an append-only amendment history. | A full-text index with relevance weights, nested sections, and an embedded `amendments` array updated atomically by a pipeline update. |

**Design rule:** MongoDB never copies data that MySQL owns. Documents refer to MySQL
rows by integer ID (`case_id`, `doctor_id`, `staff_id`, `treatment_id`, ...). Names,
beds and bills are always read from MySQL, so there is one source of truth for each fact.

## 2. Collections

Database: `hospital_emergency_management` (set with `MONGODB_DB`).

| Collection | One document is | Sample documents | Links to MySQL |
|---|---|---|---|
| `incident_reports` | one incident (prehospital call-out or in-hospital safety event) | 8 | `case_ids[]` → `EMERGENCY_CASE`, `reported_by` / `follow_up.reviewed_by` → `DOCTOR` / `NURSE_STAFF` |
| `observation_logs` | one set of vital signs taken at one time | 32 | `case_id` → `EMERGENCY_CASE`, `recorded_by` → `DOCTOR` / `NURSE_STAFF` |
| `clinical_notes` | one clinical note | 14 | `case_id`, `author`, `links.treatment_id` / `test_order_id` / `prescription_id` |
| `counters` | the last incident number used in a year | created on first use | none |

### 2.1 `incident_reports`

| Field | Type | Rules |
|---|---|---|
| `incident_no` | string | `INC-YYYY-NNNN`, unique. Generated by an atomic counter, never typed by the user |
| `category` | enum | `prehospital` or `in_hospital` |
| `incident_type` | enum | 16 values, e.g. `medical_cardiac`, `road_traffic`, `patient_fall`, `medication_error` |
| `case_ids` | int[] | at least 1, unique items; several cases for a multi-casualty incident |
| `occurred_at`, `reported_at` | date | |
| `reported_by` | `{doctor_id}` or `{staff_id}` | exactly one key |
| `location.description` | string | 3–200 characters |
| `location.geo` | GeoJSON Point | `[longitude, latitude]` within valid ranges; **required for prehospital** |
| `severity` | enum | `low`, `moderate`, `high`, `critical` |
| `harm_level` | enum | `none`, `minor`, `moderate`, `severe`; **required for in-hospital** |
| `summary` | string | 10–1000 characters |
| `details` | object | free shape, depends on `incident_type` |
| `timeline[]` | `{event, at, note?}` | event from a fixed list (`call_received` … `closed`) |
| `status` | enum | `open` → `under_review` → `closed` (forward only) |
| `follow_up` | `{actions[], reviewed_by, closed_at}` | set when the incident is closed |
| `schema_version`, `created_at`, `updated_at` | int, date, date | |

The validator uses `oneOf` for the category rules: a prehospital report must have a
map location and a timeline, and an in-hospital report must have a harm level.

### 2.2 `observation_logs`

| Field | Type | Rules |
|---|---|---|
| `case_id` | int | ≥ 1 |
| `observed_at` | date | not in the future (checked by the builder) |
| `source` | enum | `prehospital`, `triage`, `ward` |
| `recorded_by` | `{doctor_id}` or `{staff_id}` | taken from the signed-in user |
| `vitals.heart_rate` | int | 20–250 |
| `vitals.resp_rate` | int | 4–60 |
| `vitals.spo2` | int | 50–100 |
| `vitals.on_supplemental_o2` | bool | |
| `vitals.bp.systolic` / `diastolic` | int | 40–300 / 20–200 |
| `vitals.temp_c` | number | 30–45 |
| `vitals.consciousness` | enum | ACVPU: `A`, `C`, `V`, `P`, `U` |
| `vitals.gcs` | int | 3–15 |
| `vitals.pain_score` | int | 0–10 |
| `additional` | object | free shape (peak flow, pupils, glucose, ...) |
| `notes` | string | ≤ 1000 characters |

`vitals` needs at least one reading, and no other keys are allowed inside it. A reading
is identified by `(case_id, observed_at, source)`, which is a unique index.

### 2.3 `clinical_notes`

| Field | Type | Rules |
|---|---|---|
| `case_id` | int | ≥ 1 |
| `note_type` | enum | `triage`, `assessment`, `progress`, `procedure`, `handover`, `discharge` |
| `author` | `{doctor_id}` or `{staff_id}` | taken from the signed-in user |
| `title` | string | 3–150 characters |
| `body` | string | 1–10 000 characters |
| `sections` | object of strings | optional SOAP parts |
| `tags` | string[] | lowercase `a-z0-9-`, unique, ≤ 20 |
| `status` | enum | `draft` → `signed` → `amended` |
| `signed_at` | date | required once signed (`allOf` rule) |
| `amendments[]` | `{amended_at, amended_by, reason, previous_body}` | required when `status` is `amended`; append-only |
| `links` | object | `treatment_id`, `test_order_id`, `prescription_id`, `incident_no` |

### 2.4 Validation summary

* Every collection has a `$jsonSchema` validator with `validationLevel: strict` and
  `validationAction: error`. An invalid insert or update is **rejected by the server**
  with error 121, whatever program sends it (the app, mongosh or Compass).
* `additionalProperties: false` on the outer document means a field from MySQL (for
  example `patient_name`) cannot be copied in by mistake.
* Every document has `schema_version: 1`, so a later change of shape can be migrated safely.
* The builders in `lib/queries.js` add the checks a validator cannot make: a reading
  must not be in the future, `reported_at` cannot be before `occurred_at`, and the
  case ID must be a positive integer.

## 3. Indexes

| Collection | Index | Used by |
|---|---|---|
| incident_reports | `uniq_incident_no` (unique) | look-up by number, duplicate protection, counter seeding |
| incident_reports | `case_ids` (multikey) | F4 incidents for a case, A6 timeline |
| incident_reports | `category_type_occurred` | trend reports filtered by type |
| incident_reports | `status_occurred` | F3 work queue |
| incident_reports | `location_geo_2dsphere` | A4 hotspots (`$geoNear`) |
| observation_logs | `uniq_case_observed_source` (unique) | F1 case chart, A1 NEWS2 board, double-submit protection, D2 delete |
| observation_logs | `observed_at` | F2 red flags in a time window |
| clinical_notes | `case_created` | F7 notes for a case |
| clinical_notes | `notes_text` (text: title ×5, tags ×3, body ×1) | F5 full-text search |
| clinical_notes | `draft_queue` (partial: drafts only) | F6 sign-off queue |
| clinical_notes | `author_doctor_created` (partial) | notes by a doctor |

The integration tests check, with `explain()`, that each query uses its intended index
and does not fall back to a collection scan.

## 4. Retrieval strategy

All queries are built in one place, `lib/queries.js`, and are used unchanged by the
API (`lib/repository.js`), the demo runner (`npm run queries`), the generated mongosh
file and the documentation (`docs/QUERIES.md`).

| Need | How it is read |
|---|---|
| A case's chart, notes, incidents | `find` on the case ID, served by an index and sorted by time |
| Who needs urgent review | F2 red-flag filter and the A1 NEWS2 board (scored in the pipeline, previous score via `$setWindowFields` + `$shift`) |
| Searching notes | `$text` search ranked by `textScore` |
| Dashboards | `$facet` (several panels in one round trip), `$dateDiff`, `$bucket`, `$geoNear` |
| Whole story of a case | `$unionWith` merges the three collections into one timeline |

When the app needs MySQL facts with MongoDB facts, for example the patient name on
the NEWS2 board, the API runs the MongoDB query, collects the `case_id`s and fetches
those rows from MySQL in one `WHERE case_id IN (...)` query.

## 5. Create, update and delete rules

| Operation | Rule enforced by the filter or builder |
|---|---|
| C1 record observation | `recorded_by` taken from the session; a duplicate reading is rejected (11000) |
| C2 report incident | number from the atomic counter; always starts `open` |
| C3 write note | always starts `draft` |
| U1 close incident | only incidents that are not already closed |
| U2 sign note | only drafts, and only your own (enforced in the repository) |
| U3 amend note | pipeline update archives the old body in the same atomic write |
| U4 start review | only `open` incidents (status moves forward only) |
| U5 edit draft | only your own drafts |
| D1 delete draft | only your own drafts; **signed notes can never be deleted** |
| D2 delete observation | only the person who recorded it, by its unique key |
| D3 purge incidents | admin only; only `closed`; must be older than the retention period (365 days by default) |

### Incident numbers (`counters` collection)

`repository.nextIncidentNo()` keeps one document per year, `{ _id: "incident_no:2026", seq: 8 }`.
It first raises `seq` to the highest number already in use (`$max`), then
increments it atomically (`findOneAndUpdate` + `$inc`). Two people filing at the same
moment always get different numbers. The integration test files three reports
concurrently and checks they get 0009, 0010 and 0011.

## 6. Transactions

`repository.closeIncidentWithNote()` closes an incident **and** writes the signed
review note for the patient's case in one multi-document transaction
(`session.withTransaction`, snapshot read concern, majority write concern). If the
note fails validation, the incident is not closed either.

MongoDB supports multi-document transactions only on a replica set. On a standalone
server the function returns HTTP 501 with an explanation, and nothing is changed. To
enable transactions on a local server:

```bash
mongod --replSet rs0 --dbpath <your data folder>
mongosh --eval "rs.initiate()"
# connection string: mongodb://localhost:27017/?replicaSet=rs0
```

MongoDB Atlas clusters, including the free tier, are replica sets already.

## 7. Role-based access control

`lib/access.js` holds one permission table, which is used in two places:

1. **In the application**: every repository function calls `assertCan(user, action)`
   first. The author or recorder is always taken from the signed-in user (`actorRef`),
   never from the request body.
2. **In the database**: `npm run roles` creates MongoDB roles with collection-level
   privileges generated from the same table.

| Permission | doctor | nurse | admin |
|---|:-:|:-:|:-:|
| read / record / delete own observations | ✓ | ✓ | |
| read / write / edit / sign / delete own draft notes | ✓ | ✓ | |
| amend signed notes | ✓ | | |
| read incidents, operational reports | ✓ | ✓ | ✓ |
| file incidents | ✓ | ✓ | |
| review / close incidents | ✓ | | ✓ |
| purge closed incidents | | | ✓ |
| clinical reports (NEWS2, vitals, timeline) | ✓ | ✓ | |

MongoDB roles (`npm run roles -- --print` shows the exact privileges):

| Role | Privileges |
|---|---|
| `hospital_er_doctor` | clinical_notes find/insert/update/remove; observation_logs find/insert/remove; incident_reports find/insert/update; counters find/insert/update |
| `hospital_er_nurse` | clinical_notes find/insert/update/remove; observation_logs find/insert/remove; incident_reports **find/insert only**; counters find/insert/update |
| `hospital_er_admin` | incident_reports find/update/remove **only** (no clinical data) |
| `hospital_er_app` | inherits the three roles above. This is the account the Next.js server uses: it cannot drop collections, change validators or manage users |

Users are created with `npm run roles -- --users`. Their passwords come from
`MONGODB_*_PASSWORD` environment variables, and MongoDB stores only a salted
SCRAM-SHA-256 hash. Roles are enforced once `mongod` runs with authentication enabled
(`security.authorization: enabled`). Atlas always enforces them; there, the custom
roles are created in **Database Access → Custom Roles**.

## 8. Consistency with MySQL

`tests/consistency.test.js` reads `../02_sample_data.sql` and checks the sample data:

* every `case_id`, `doctor_id` and `staff_id` in MongoDB exists in MySQL
* note links point to treatment, test and prescription rows **of the same case**
* prehospital records exist only for ambulance arrivals and end at the case's `arrival_time`
* notes are written after the patient arrived, and timestamps are in order
* no MySQL column (patient names, phone numbers, ...) is duplicated into MongoDB

At run time, the API passes `options.caseExists` to the repository. It checks the case
in MySQL before any MongoDB write, and returns 404 if the case does not exist.
